Part One

Development Plan

Core principle: The rules engine is built before anything else that touches gameplay. UI, AI, networking, and Story Mode are all consumers of it. Order is specific to avoid refactors later.

The architecture follows a strict separation: Data (card definitions, game config) → Logic (rules engine, game states) → Presentation (board UI, menus). The rules engine is written in pure C# with zero Unity dependencies so it can be tested in isolation, the AI can reason over it cleanly, and the network layer can synchronise it without complexity.

Communication between the logic and visual layers flows through a Command Queue. When the logic layer changes game state, it dispatches a Command object. Commands are executed sequentially - each one completes (including any animation) before the next begins. This means the logic layer can resolve effects instantly while the visual layer plays them out at its own pace, keeping the two fully decoupled.

Foundation & Data Architecture

Build the skeleton everything else hangs off

Card Data Model

Every card lives as a typed data asset. Each card type - Spirit, Spell, Secret, Ritual, Curse, Prayer: has its own definition inheriting from a shared base, covering name, type, supertype, spirit rank (Spirits only), gold status, artwork reference, and an effects list.

Effects are also data objects, not hardcoded logic. A “Steal 2” effect is a typed object with a value of 2 - it isn’t a function written specifically for that card. This is what makes adding new cards later seamless: new cards are authored data, not new code.

The three numeric value types in the rules require distinct representations in the data model:

TypeExampleCan Modifiers Change It?
Symbolic1, 2, 3Yes
Word-formone, two, threeNo - permanently fixed
X“Steal X souls”Yes - value chosen at play time

Game State Model

A single serialisable C# class holds the complete live state of any game: both players’ soul totals, hands, decks, discard piles, field zones, the spirit pool state, the resolution pile, whose turn it is, current phase, action counts, active modifiers, and all counters. This is the object sent across the network and the object the AI reads from. Zero Unity dependencies.

Counters are also tracked per card in the game state. A counter is a marker placed on Field cards only; counters cease to exist if the card leaves the Field, and counters on a card that Merges onto a host also cease to exist (the host’s own counters remain unaffected).

Ownership & Control Tracking

The rules distinguish between who owns a card (the player who put it in their deck - never changes) and who controls it (the player who currently has it on the field - can change). The word “you” in any effect text always refers to the controller. Both are tracked in the game state from the start.

Zone System

Each zone - Main Deck, Hand, Discard Pile, Spirit Zone, Incantation Zone, Sorcery Zone, Resolution Pile, and the Side Game zone (for Namara’s special cards) - is a typed class. Cards do not move themselves; all zone transitions are explicit operations dispatched through the rules engine. The Discard Pile preserves insertion order - several card effects interact with the top one or two cards of the pile specifically.

Public vs Hidden Information

  • Public zones (all players can see): Field face-up cards, Discard Pile, Resolution Pile, Side Game zone
  • Hidden zones: Decks, each player’s Hand
  • Semi-public: Face-down cards in the Sorcery Zone are present but their identity is hidden; their count is public. Hand size is also public - a player must truthfully state it if asked.

Save System Interface

Deck data, player progression, and settings all use a single save interface written to work on both desktop (local file) and browser (browser persistent storage). All other systems call this interface - nothing writes to disk directly. This must be established in Phase 0 or it becomes a refactor later.

ID Bridge System

The logic layer works exclusively with integer IDs, never with Unity GameObjects or MonoBehaviours. When a visual representation is created for a card or player, it registers itself with a unique ID. When a Command needs to animate something - move a card, show damage, remove a creature - it looks up the relevant GameObject by ID. This is what keeps the logic layer dependency-free and testable outside of Unity entirely.

Core Rules Engine

Most complex system in the project - full implementation confirmed, everything depends on it

Turn & Round Manager

Implements the complete game sequence: Beginning of Round → Spirit pool deal → each player selects a spirit → Ready to Reveal → simultaneous reveal → ascending spirit rank determines turn order. For each turn: Start of Turn triggers (Spirit → Curses → Rituals) → Action Phase → End of Turn triggers → Draw Phase → End of Round.

The Turn & Round Manager is implemented using a state machine pattern, with each phase (BeginRound, SpiritSelection, StartOfTurn, ActionPhase, EndOfTurn, DrawPhase, EndOfRound) as a discrete state owning its own logic and transition conditions. The Resolution Stack runs as a separate peer system that communicates via events, keeping it decoupled from the state flow.

Spirit Pool System

The spirit pool depletes across rounds and only resets when fully exhausted. In a 2-player game with 12 spirits, the pool decrements by 2 each round. The deal count scales with pool size:

Pool SizeCards Dealt to Each Player
8 or more4
63
42
21 (randomly assigned)

When the pool hits zero - all 12 spirits used across six rounds - all 12 are restored and the cycle begins again.

Spirit Selection & Ready to Reveal

Each player privately selects one spirit; unchosen spirits return to the pool. The player clicks “Ready to Reveal.” When both players (or player and AI) have committed, the reveal fires simultaneously - the round-start sync point in both local and online play.

Note: Spirit cards cannot be targeted, taken, given, Destroyed, Silenced, or moved to non-Spirit zones by any effect. Spirit exchanges are only permitted as an explicit result of an effect that states so.

Action System

Each player has 2 actions per turn, spent by: playing a card face-up (Normal Play), playing a sorcery face-down (Secret Play), or revealing a face-down spell. Extra Actions from Pact effects or card text do not cost from this budget. Recycling (once per turn) and Prayer activation are not actions.

Resolution Stack

The resolution pile is a LIFO stack shared across all players. When a card is played, a sorcery is revealed, an effect is activated, or a triggered effect fires, it enters the top of the pile. Before the top item resolves, all players hold priority in ascending spirit rank order. While holding priority, a player may respond by revealing a Secret whose condition is true - the only thing that can happen during an opponent’s turn. When all players pass consecutively, the top item resolves.

In the digital version, the response/trigger check is automated - the engine performs checks before and after each game state change without players needing to call for them manually.

Bypasses the pile entirely: Recycling, Conspiracy, Put effects, Sacrifices, and all Continuous/Static effects.

Stack Interactions & Special Cases

  • Conspiracy - when a Secret with Conspiracy is revealed, its controller may Put (not Play) a face-down Sorcery from Hand onto the Field before the Secret resolves. That Put sorcery can immediately be revealed if its condition is met. Bypasses the pile entirely and cannot be Negated.
  • Secret during resolution - if a Secret’s condition is met during another effect’s resolution, the Secret’s controller may reveal it, pausing the triggering effect. After the Secret resolves, the paused effect continues if still valid.
  • Special Play - playing a card via an effect rather than as an action. The played card is placed on top of the current effect on the pile and must fully resolve before the original effect continues. Cards played from non-Hand zones via Special Play are always face-up.
  • Spell face-down - a Spell played face-down retains its Spell type underneath but is treated as a Secret while face-down. Both actual Secrets and face-down Spells are “face-down Sorceries.” Effects targeting “Secrets” vs “face-down Sorceries” interact differently - the engine must track the underlying type of each face-down card in the Sorcery zone.

Effect Dependency Categories

CategoryBehaviourExample
UnlinkedEach effect resolves independently“Silence a card. Banish 2 souls, +2 per silenced card” - Banish resolves regardless of whether Silence succeeded
LinkedEach effect requires the previous to have resolved (“If you do…”)“Destroy 1 incantation. If you do, banish 2 souls” - Banish only fires if Destroy resolved
Card IndependentActivated/Triggered effects continue even if their source card is destroyedA Prayer activated then sacrificed as its cost - the effect still resolves
Card DependentPart of the source card’s resolution - Negating the card removes these tooMost Spell effects

Effect Status System

  • Active - currently in force (static field effects, or effects currently on the pile)
  • Standby - condition-based effects waiting on the field until their condition is met, then trigger automatically
  • Silenced - a Silence effect has stripped this effect’s text; it cannot trigger or be activated

“Cannot” Rule

If a card’s text states that something cannot happen, that takes absolute precedence over any other effect or rule - including Replacement effects. These are hard stops with no exceptions.

Optional vs Mandatory Effects

Effects containing “you may” are optional. Effects with “up to X” are also optional (choosing zero causes the effect to Fizzle). Effects with neither are mandatory and must be performed if the game state allows.

Fizzle vs Negate

MechanicCauseResult
FizzlePassive failure - conditions no longer met, all targets illegal, or zero chosen for “up to X”Effect removed from pile without resolving. Nothing actively caused this.
NegateActive cancellation by another card or effectNegated card sent to owner’s Discard Pile. All Card Dependent effects on it are also Negated.

Infinite Loop Detection

If mandatory triggered effects create an infinite loop, the active player chooses a positive integer and the loop runs exactly that many times before breaking. The engine must detect looping triggered effects and surface this resolution to the player.

Target Legality at Resolution

Targets are declared when an effect enters the pile. At resolution, the engine checks all declared targets are still legal. If all targets are illegal, the effect Fizzles.

Zone Capacity Enforcement

Maximum 3 incantation slots and 3 sorcery slots per player. If a card would resolve into a full subzone, it goes to the Discard Pile instead (unless using Merge). The check happens at resolution, not at the point of play.

Specific Effect Implementations

EffectKey Implementation Notes

Game Board UI

The visual layer that is built on top of the rules engine, reflecting the current game state.

Board Layout

Two mirrored player areas per the provided art. Each side: spirit zone, three incantation slots, three sorcery slots, hand display along the bottom, deck and discard indicators. Shared centre: the spirit pool and spirit discard zone. Player HUD: soul count, Defense value, Banishing and Stealing modifiers, avatar portrait, turn timer, and action count (e.g., “Actions: 1/2”).

Reference - Game Board Scene
Prototype -Game Board (Research Build)
For the browser build, the board must render cleanly at typical browser window sizes without depending on a fixed resolution. Expensive post-processing and render textures should be avoided.
All card and creature visuals are Unity UI elements (Canvas-based) rather than 3D world-space objects. Depth and draw order are managed through Canvas sorting layers and sorting orders. This is standard practice for card games and simplifies overlap handling significantly - particularly relevant for the hand display, the resolution pile indicator, and face-down cards in the sorcery zone.

Card Rendering

Frame colour matches card type - Spirit (yellow), Spell (red), Secret (green), Ritual (blue), Curse (purple), Prayer (grey). Face-down cards show only the card back. Hand size and face-down sorcery count are always visible to both players. Face-down identities are not. Hovering a face-up card shows full text.

Player Inputs - Full Interaction List

Each card type has its own drag behaviour component rather than one monolithic input handler. Normal Play (drag to field), targeted effects (drag to target with arrow), and Secret reveals each have distinct implementations sharing a common interface. The input manager calls into whichever component is attached - it doesn’t need to know what kind of card it’s dealing with.

  • Click to select from hand → click valid zone to play (or drag from hand to zone)
  • After selecting a targeted card, eligible targets highlight - click to confirm
  • When a card offers two effects (OR), a choice modal appears before the card enters the pile
  • “Are you sure?” confirmation prompts where the rules specify
  • “Pass Priority” button whenever a player holds priority
  • “Respond” trigger when a player holds priority and has a valid Secret in play
  • Select a play option when applicable (Normal Play, Secret Play, Merge)
  • Sacrifice prompt when activating a Prayer - choose a card to sacrifice or confirm 3-soul cost
  • “Choose top 2 cards of discard pile” selection UI for relevant card effects
  • Conspiracy: select face-down sorcery from hand to Put onto the field
  • Pass phase / end action phase
  • Open in-game options menu

Resolution Pile Display

A visible indicator shows items on the pile top-to-bottom. The current top item awaiting resolution is clearly distinguished. Players can see what is pending and what the last resolved effect was.

Ready to Reveal

Each player’s selected spirit shows as a face-down indicator during selection. Once both commit, “Ready to Reveal” triggers the simultaneous reveal - doubling as the round-start sync point in online play.

Construction Rules Enforced

  • 40–60 cards per main deck
  • Maximum 3 copies of any card name across main deck and side deck combined
  • Maximum 1 Gold card in the main deck; maximum 2 Gold cards across both decks combined
  • Side deck capped at 10 cards

Save / Load

AI Opponent

Required for Story Mode and Arena practice - built on top of the rules engine

How the AI Works

The AI reads from a view of the game state that reflects only what it would legitimately know: its own hand, the visible field state, soul totals, active modifiers, and the face-up discard pile. It does not know the opponent’s hand or either deck order.

The AI is deck-aware and board-reactive: it has full knowledge of its own card list and the optimal plays for a given hand configuration, but adjusts decisions based on the live board state.

Implementation Approach

The AI uses a weighted action scoring system rather than a computationally heavy search algorithm (important for browser performance). For every legal action available on its turn, the AI calculates a score:

ComponentWhat It Evaluates
Base card valueA fixed value authored per card reflecting its general strength
Situational modifiersDoes this Steal get reduced by their Defense? Does a Pact chain off the current Spirit? Is the opponent’s soul total low enough that this ends the game?
Board state modifiersAvailable field slots, active modifiers, what Secrets the AI currently holds, current soul differential

Action Evaluation

  • Action priority order - lethal detection first (can I win this turn?), then defensive plays if under threat, then offensive progression
  • One-step look-ahead - after selecting the highest scoring action, the AI simulates it to confirm it doesn’t walk into a bad board state
  • Resolution pile responses - handled as a separate system; the AI weighs the cost of letting the current stack item resolve against the value of responding, including whether holding the Secret for a better moment is stronger
  • Spirit selection - scored in isolation per round; each available Spirit is weighed by effect value vs the turn-order advantage of going first

Difficulty Tiers

Two tiers: a Story Mode tier that deliberately makes sub-optimal early choices to ease players in, and a full-strength Arena tier. Both use the same underlying framework with a configurable error rate parameter.

Story Mode Extensions

Each encounter can override standard rules - time limits, specific win conditions, soul-at-stake multipliers, Steal and Banish modifiers, multi-opponent configuration. The AI reads these encounter parameters and plays accordingly.

TurnMaker Pattern

The AI follows the same TurnMaker pattern as the human player - an abstract base class with a player subclass and an AI subclass, each overriding the turn start behaviour. The AI subclass runs its decision logic, dispatches the same Command objects a human player would, and ends its turn through the same interface. From the rules engine’s perspective, there is no difference between a human action and an AI action.

Story Mode

Stripped-down campaign - 1v1 vs AI only, single Duel format, no Best-of-3

World Map

A static map with authored encounter nodes. Green nodes are next available main story encounters (free to enter). Blue nodes are optional side encounters costing Gold Coins to access. Node connections are authored data - no pathfinding, only node selection.

Reference - Campaign Map Scene

Encounter System

Each encounter is a self-contained data object: the opponent’s deck, their avatar, the soul-at-stake multiplier (X), any special battle conditions, and the rewards on victory. The game scene loads with the rules engine configured to that encounter’s parameters. Special conditions are modular overrides on top of the standard rule set.

Player Progression

ResourceGained BySpent On
SoulsWinning battles, selling cardsLevelling up, purchasing cards in Soul Forge, wagered in battles
Gold CoinsBattle rewards, NPC exchangesAccessing blue optional map nodes, NPC trades

Player level gates map progression and Soul Forge card access. Player rank (Bronze → Silver → Gold → Initiate → Master → Grand Master, each with tiers) unlocks specific in-game events and awards a random Gold card on each promotion.

Loss Penalty

On a battle loss: the player loses (30 × X) souls, where X is set per encounter, plus the remaining soul total of defeating opponents. If total souls reach zero, it is game over and full progression resets - unless Easy Mode is active.

Easy Mode

Toggled at profile creation. Prevents the player’s total souls from ever reaching zero (floors at 1), making a full game-over reset impossible. No other rules are changed.

Save System

Autosave per chapter plus a manual chapter save. Uses the shared save interface (desktop and browser compatible).

Networking - 1v1 Online

Technology: Photon · Host/Join model

Connection Options

  • Host & Join - one player creates a session and shares a short room code; the other player enters it to connect
  • Quick Join - player enters a queue and is automatically connected to the first available host; times out if no host is found within a set window

No ranked matchmaking, leaderboards, or tournament systems in the prototype.

Synchronisation

The host runs the authoritative game state. Clients send input events - card played, target selected, priority passed, spirit selection committed - to the host. The host validates each input against the rules engine, updates the game state, and broadcasts the result. The resolution pile requires the host to manage which player holds priority and gate inputs accordingly.

Disconnection

A player who disconnects or is inactive for one minute automatically loses. No reconnection in the prototype - the session ends and the remaining player wins.

Photon supports browser builds, but the specific transport layer depends on which Photon product is chosen. Browser compatibility must be confirmed before Phase 6 begins.

Soul Forge

Card collection display and acquisition, avatar selection - core functionality only

Cards

The Soul Forge displays cards available for the player’s collection, gated by player level. Cards are purchased with Souls. The card grid mirrors the Deck Builder browser. Purchasing is a live transaction - Souls are deducted, the card is added to the collection, and it becomes available in the Deck Builder immediately.

Avatars

Players select an avatar at profile creation and can change it from the Soul Forge. The selected avatar persists to the player profile and appears in the HUD and menus during games. Avatars available for prototype.

Legend Forge

A visible but locked placeholder for the prototype. Marked as coming soon within the UI.

Tutorial

Built once all systems stable, using the final rules engine

Structure

An interactive walkthrough covering: the game’s objective, card types and zones, spirit selection and the Ready to Reveal flow, the round and turn sequence, playing a card, the resolution pile and how priority works, responding with a Secret, core effects (Steal, Banish, Defense), and the win condition.

Implementation

A tutorial controller overlays guidance prompts directly on the live game scene using a scripted opponent - not the AI - that plays a predetermined sequence of cards. Each step restricts available inputs and advances when the player takes the correct action. Because the tutorial runs on top of the real rules engine, what players learn is exactly how the game works.
